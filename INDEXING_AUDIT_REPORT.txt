CORRECTION TO THE ORIGINAL BRIEF
--------------------------------------------------------------------------------
The GSC export shows the dominant problem is NOT "Crawled - currently not
indexed" — that status holds exactly 1 page. 132 pages (97% of the issue) are
"Discovered - currently not indexed": Google knows these URLs exist but has
not crawled them at all yet. That is a crawl-priority / site-trust signal,
not a "Google looked and rejected it" signal. The two have different fixes,
so this report is built around the status the data actually shows.

Also correcting the brief's assumption of an EN/FR/AR site: the codebase
only supports EN and FR (SUPPORTED_LANGUAGES = ['en', 'fr']). No Arabic
routes exist, live or in code. Two places DID falsely claim Arabic as a
served language in structured data (schema.js's Organization contactPoint
and AirportTransferDetailPage.jsx's Service availableLanguage, both
'availableLanguage: [en, fr, ar]') — this has been fixed (Section 3.5); every
other reference to 'ar' found in the codebase was a false-positive substring
match (e.g. "car", "nearby"), not real Arabic-locale code.

================================================================================
1. ROOT CAUSE
================================================================================
Nothing in the technical layer is blocking or misdirecting crawlers —
robots.txt, meta robots, canonical tags, hreflang, and server-side rendering
all check out clean across a full 144-URL sitemap sweep. Every page fetched
returns HTTP 200 with unique titles, meta descriptions, H1s, and fully
server-rendered content. That rules out the usual suspects for a young,
low-authority site: this is a crawl-priority and content-density problem,
not a technical block.

Three compounding factors explain why Google is choosing not to spend crawl
budget on 132 of ~142 pages:

1. LOW SITE AUTHORITY / EARLY TRUST TIER
   Only 9 of 142 pages are indexed and daily impressions are in the
   single-to-low-double digits. Google throttles crawl frequency on sites
   it hasn't yet built confidence in — this is the base rate the other two
   factors compound on top of.

2. A 31-PAGE TOUR CLUSTER WAS TEMPLATED — NOW REWRITTEN AROUND ITS OWN
   TARGET QUERY [FIXED]
   The 7-8 Marrakech day-trip pages shared 70-88% identical visible text
   (verified by line-diffing live HTML) — identical itinerary structure,
   identical inclusion/exclusion lists, one shared "Overview" sentence
   template reused across all 31 tours. Only the H1, 3-4 highlight bullets,
   and the FAQ block were genuinely unique per page. Each page's title and
   tagline already implied a distinct target query (e.g. "Essaouira day trip
   from Marrakech," "Day Trip to Ait Ben Haddou from Marrakech," "Ouzoud
   Waterfalls... Morocco's tallest") — the body copy just didn't back that
   query up with matching, page-specific detail. Every one of the 8 pages
   (plus the marrakech-day-trips hub) now has an authored `overview`
   paragraph and a real 4-step itinerary naming what's actually distinctive
   about that destination — the UNESCO ramparts and argan groves for
   Essaouira, the Tizi n'Tichka pass and film-location history for Ait Ben
   Haddou, altitude and Toubkal-trailhead framing for Imlil, and so on —
   in both EN and FR. See Section 4 for the full before/after per page.

3. THAT SAME CLUSTER WAS INTERNALLY UNDER-LINKED [FIXED]
   getRelatedTours() always returned the first three same-category tours in
   array order, never rotated. Of the 10 day-trip tours, only the first 3
   in the source file ever appeared in another page's "Related tours" widget
   — the other 7 got exactly one inbound internal link sitewide: their own
   card on the /day-trips listing page. Fixed by rotating the same-category
   slice by each tour's own position in the catalog, so every tour in a
   10-tour category gets picked as "related" somewhere instead of the same
   2-3 tours absorbing all the inbound link equity. See Section 3.1.

These three factors reinforce each other: a low-trust site is exactly the
kind of site where Google's crawler is least forgiving of a thin,
weakly-linked cluster — it deprioritizes crawling those pages rather than
fetching and then rejecting them, which is why "Discovered" (132) dwarfs
"Crawled" (1) rather than the reverse.

3. TECHNICAL FIXES
================================================================================
Status: 3.1, 3.3, 3.4 and 3.5 are implemented on branch
fix/indexing-audit-remediation and verified (build, lint, and the project's
own automated checks all pass). 3.2 is a hosting-layer change outside this
codebase and is not shipped here — it needs to be made in the Hostinger/hcdn
configuration directly.

--------------------------------------------------------------------------------
3.1 Rotate the related-tours selection instead of always picking the first 3 [DONE]
--------------------------------------------------------------------------------
FILE: apps/web/src/data/tours/index.js — getRelatedTours()

CURRENT:
    const sameCategory = others.filter((entry) => entry.categoryKey === current.categoryKey);
    const rest = others.filter((entry) => entry.categoryKey !== current.categoryKey);
    return [...sameCategory, ...rest].slice(0, limit);

CHANGE TO:
    const sameCategory = others.filter((entry) => entry.categoryKey === current.categoryKey);
    const rest = others.filter((entry) => entry.categoryKey !== current.categoryKey);
    // Rotate the starting point by the current tour's position so every tour in a
    // category gets picked as "related" somewhere, instead of the same first 3
    // absorbing every inbound link and the rest going unlinked.
    const startIndex = tours.findIndex((entry) => entry.slug === slug) % Math.max(sameCategory.length, 1);
    const rotated = [...sameCategory.slice(startIndex), ...sameCategory.slice(0, startIndex)];
    return [...rotated, ...rest].slice(0, limit);

WHY: today, every page in a category shows the identical first-3-in-array
related tours. In the 10-tour day-trips category, 7 tours never appear in
anyone's related widget — their only inbound link sitewide is their own
listing-page card. Rotating the start index by each tour's own position
spreads inbound links across the whole category instead of concentrating
them on 2-3 tours.

--------------------------------------------------------------------------------
3.2 Normalize the root and language-root trailing slash at the edge [OPEN]
--------------------------------------------------------------------------------
LOCATION: Hosting layer (Hostinger/hcdn) — not an application-code fix

CURRENT:
    /           -> 200 (duplicate of /en)
    /en         -> 200 (canonical target)
    /en/        -> 200 (duplicate, does not redirect)
    /fr/        -> 200 (duplicate, does not redirect)

CHANGE TO:
    /           -> 301 -> /en
    /en         -> 200 (canonical target, unchanged)
    /en/        -> 301 -> /en
    /fr/        -> 301 -> /fr

WHY: every other route on the site correctly 301s a trailing slash to the
clean URL (/en/about/ -> /en/about) except the bare root and the two
language roots. The <Seo/> component already emits a correct
self-referencing canonical on all four variants, so this isn't causing
duplicate indexing — but it is 4 extra crawl events for zero benefit on a
142-URL site where crawl budget is already the binding constraint. Low
severity, cheap to fix, worth doing alongside the higher-priority items.

--------------------------------------------------------------------------------
3.3 Give LocalBusiness its own @id [DONE]
--------------------------------------------------------------------------------
FILE: apps/web/src/seo/schema.js — lines 70, 139

WAS:
    // buildTravelAgencySchema()
    '@id': `${SITE_ORIGIN}/#localbusiness`

    // buildLocalBusinessSchema()
    '@id': `${SITE_ORIGIN}/#localbusiness`   // same id, different @type

NOW:
    // buildTravelAgencySchema()
    '@id': `${SITE_ORIGIN}/#travelagency`

    // buildLocalBusinessSchema()
    '@id': `${SITE_ORIGIN}/#localbusiness`   // now the sole owner of this id

WHY: both schema builders emitted the identical @id for two different @type
declarations (TravelAgency vs LocalBusiness), on every single page
site-wide. Per JSON-LD conventions one @id should resolve to one entity.
Google's parser is generally tolerant of this, so it's unlikely to have been
blocking indexing on its own — but it was a real correctness defect. The one
cross-reference at schema.js:255 (buildTourSchema's offers.provider) still
correctly points at #localbusiness (unchanged) — it references the more
complete commercial entity (address/geo/opening hours), not the one that
was renamed.

--------------------------------------------------------------------------------
3.4 Merge sitemap-reviews.xml into sitemap-pages.xml [DONE]
--------------------------------------------------------------------------------
FILES: apps/web/tools/generate-sitemap.mjs, apps/web/src/seo/sitemap.js

WAS:
    writeSitemap('sitemap-reviews.xml', reviewEntries);
    // ...and separately included again in sitemap-pages.xml
    // SITEMAP_FILES included 'sitemap-reviews.xml'

NOW:
    // The reviewEntries block and its writeSitemap('sitemap-reviews.xml', ...)
    // call were removed entirely. /en/reviews and /fr/avis already appear in
    // sitemap-pages.xml via the static route table, so nothing was lost.
    // SITEMAP_FILES no longer lists 'sitemap-reviews.xml'.

WHY: /en/reviews and /fr/avis were listed in both sitemap-pages.xml and
sitemap-reviews.xml. Not invalid per the sitemap spec, but it was dead
weight on a site where every unnecessary URL competes for the same limited
crawl budget. Verified by re-running the generator: sitemap-index.xml now
lists 5 children instead of 6, and the reviews URLs are still present (and
now only present) in sitemap-pages.xml. The stale sitemap-reviews.xml file
in apps/web/public/ has been deleted; the next production deploy will not
regenerate it.

--------------------------------------------------------------------------------
3.5 Stop claiming Arabic as a served language in structured data [DONE]
--------------------------------------------------------------------------------
FILES: apps/web/src/seo/schema.js (line 43),
       apps/web/src/pages/AirportTransferDetailPage.jsx (line 168)

WAS:
    availableLanguage: ['en', 'fr', 'ar']

NOW:
    availableLanguage: ['en', 'fr']

WHY: the site has no Arabic routes — SUPPORTED_LANGUAGES in seo/sitemap.js
is ['en', 'fr'] only — but the Organization.contactPoint schema (emitted on
every page site-wide) and the airport-transfer pages' Service schema both
claimed 'ar' as an available contact language. Search engines and AI answer
engines treat availableLanguage as a factual capability signal; claiming a
language the site can't actually serve is a real accuracy defect, not
optimization. Verified via airport:check (12/12 pages still pass with
availableChannel=true after the change).

8. TRUST SIGNALS — ON-SITE AND OFF-SITE
================================================================================
Not part of the original GSC-driven diagnosis, but relevant to the same
underlying constraint identified in Section 1: this is a low-authority site
in Google's early trust tier, and crawl budget is allocated in proportion to
that trust. Content and internal-linking fixes address the demand side
(making pages worth indexing); trust signals address the supply side
(making Google willing to spend more crawl budget on this domain at all).
None of this is implemented — it requires business decisions the client
needs to make, listed here as a recommendation set grounded in what's
already on the site versus what's missing.

--------------------------------------------------------------------------------
8.1 ON-SITE
--------------------------------------------------------------------------------
- REVIEW VOLUME IS THE SINGLE WEAKEST SIGNAL FOUND. The site's own
  TripAdvisor data (apps/web/src/data/tripadvisor.js) shows a 5.0/5 rating
  but only 43 reviews, ranking #199 of 2,160 Transportation listings in
  Marrakech — a perfect score with a rank that low means the ranking
  algorithm is weighting volume far more than the score itself. A perfect
  rating on 43 reviews reads as under-reviewed, not exceptional, to both
  users and algorithms. This is the highest-leverage single fix available:
  prioritize a systematic post-trip review request (WhatsApp follow-up,
  timed email) over any other trust-signal work below.

- AUTHOR/EXPERTISE SIGNALS ARE MISSING FROM BLOG CONTENT. BlogArticlePage.jsx
  renders post.author.name and post.author.role when present (confirmed in
  ArticleMeta, lines 48-56), but this is optional per-post data — worth
  auditing whether all 7 blog posts actually populate it, and pairing it
  with something Google's E-E-A-T signals reward: a short author bio linking
  to a real person's on-the-ground experience in Morocco, not a generic
  "Yassine Travel Team" byline.

- THE "18+ YEARS EXPERIENCE" / "SINCE 2008" CLAIM (used in tour-page trust
  strips and footer copy) has no supporting on-site evidence — no About
  page timeline, no founding story, no press mentions. If the claim is
  true, it's underused; a short verifiable history on the About page
  strengthens both user trust and E-E-A-T without new content strategy.

- STRUCTURED DATA IS ALREADY STRONG (Organization, LocalBusiness,
  TravelAgency, aggregateRating, Review schema on airport pages) and does
  not need more added — the fixes in Section 3.3/3.5 corrected what was
  there rather than expanding it. Priority is fixing review volume
  (8.1) which aggregateRating actually reports on, not adding new schema
  types.

- SECURITY/BUSINESS-LEGITIMACY SIGNALS ARE PARTIALLY PRESENT: HSTS,
  security headers and HTTPS are all correctly configured (confirmed in the
  technical crawl). "Licensed Moroccan Travel Agency" appears in tour-page
  trust strips as copy, but there's no verifiable license number or
  registration reference a skeptical visitor (or an AI answer engine
  evaluating trustworthiness) could check independently.

--------------------------------------------------------------------------------
8.2 OFF-SITE
--------------------------------------------------------------------------------
- GOOGLE BUSINESS PROFILE was not checked this session (no access) — this
  is NOT VERIFIED but is worth confirming exists and is fully optimized
  (category, hours, photos, Q&A, posts) before any other off-site work,
  since GBP signals feed directly into local trust and often correlate with
  a domain's perceived legitimacy even for non-local-pack queries.

- BACKLINK PROFILE was not audited this session (NOT VERIFIED) — for a
  site this young, a handful of genuine links from real Morocco travel
  publications, tourism board resources, or a listing in reputable travel
  directories (not link-farm submissions) would do more for crawl-budget
  trust than a large volume of low-quality links. This is explicitly
  the kind of work Section 10 (Do Not Do) warns against doing the wrong
  way — quality and relevance over volume.

- SOCIAL PROFILE COMPLETENESS: SOCIAL_LINKS (apps/web/src/data/site-config.js)
  currently covers Instagram, Facebook and TikTok, all real accounts
  (confirmed correctly referenced in Organization.sameAs, not placeholder
  '#' links). No YouTube or LinkedIn presence — YouTube in particular is
  worth considering given the visual nature of desert-camp/riad content,
  and sameAs entries compound as trust signals the more consistently a
  brand identity resolves across platforms.

- NAP (NAME/ADDRESS/PHONE) CONSISTENCY across TripAdvisor, Google Business
  Profile, and any directory listings was not audited this session (NOT
  VERIFIED) — worth a manual pass to confirm the address in
  CONTACT.streetAddress (apps/web/src/data/contact.js) matches exactly
  what's listed everywhere else the business appears online; inconsistent
  NAP is a known trust-signal degrader for local/regional businesses.
